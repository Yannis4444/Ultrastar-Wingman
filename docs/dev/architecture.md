# Architecture Principles & Extension Points

This guide sets principles and names the seams that must stay open. It is
**not** a concrete design — designs are planned per feature and discussed with
the user first (see plan.md).

## Principles

1. **Modular by seam, not by everything.** The seams listed below get a real
   interface from day one because plan.md promises future implementations.
   Everything else follows YAGNI: no abstraction until a second implementation
   exists.
2. **The backend owns all state.** USDX is an external process we drive; never
   rely on USDX-owned storage for data we care about (the old project stored
   stats in USDX's DB — that was a mistake we're fixing). Wingman's own SQLite
   database is the single source of truth for players, scores, playlists,
   settings, and song metadata.
3. **One process, layered.** FastAPI app → service layer (business logic) →
   adapters (USDX, song sources, yt-dlp, DB). Handlers stay thin: parse,
   authorize, call a service, return. Services never import FastAPI.
4. **Frontend talks only to the REST API / WebSocket.** No hidden side
   channels; whatever the UI can do, an external client (the future NFC
   selector, scripts) can do through the same API.

## Extension points (interfaces required from day one)

| Seam | Now | Later (keep possible) |
|---|---|---|
| Song source | USDB (usdb.animux.de) | USDB.eu, local folders, UltraSinger |
| Media downloader | yt-dlp (self-updating) | other fetchers |
| Karaoke launcher | Ultrastar Deluxe | other USDX forks |
| Player selector | built-in web UI | NFC tag device via REST API |
| Auth provider | local accounts | OIDC (Keycloak) |
| Settings | file/DB-backed registry | new settings without schema surgery |

An extension point is a small Python ABC/Protocol in its own module, with
implementations registered in one place (a plain dict/registry — no plugin
framework, no entry-points machinery until a third-party actually needs to
plug in from outside the repo).

## Identity

- **Song IDs**: globally unique within Wingman, stable across restarts, and
  source-scoped so provenance is never lost — conceptually
  `(source, source_song_id)` (e.g. `usdb:1234`), plus a content-level identity
  (artist + title normalized) to detect the same song from different sources.
  The exact scheme is decided in the feature plan, but any scheme must answer:
  "is this downloaded folder the same song as USDB #1234?"
- **Player/user IDs**: opaque, generated by Wingman (UUIDs), never derived
  from display names. Display names change; IDs don't. Statistics, playlists,
  favorites, and NFC tags all reference the ID.

## Permissions

- Permission checks live in one place (FastAPI dependencies) and are named by
  capability (`downloads.manage`, `playlists.manage`, …), not by role. Roles are
  bundles of capabilities.
- The host UI (the TV where USDX runs) is always admin — model this as a
  trusted local session, not a hardcoded bypass inside individual handlers.

## Concurrency & the outside world

- USDX interaction, downloads, and yt-dlp updates are long-running: run them
  as tracked background tasks with observable state (queued / running / failed
  / done) exposed over the API and WebSocket — never fire-and-forget.
- Everything that touches the network or the USDX process must tolerate
  failure and report it to the UI; no silent retries without a visible status.
