# Ultrastar Wingman

Companion app for Ultrastar Deluxe (USDX): song downloads, player management,
statistics, and a web UI for controlling karaoke sessions. Ground-up rewrite of
`D:\git\ultrastar-wingman` — the old project is inspiration for behaviour and
for the visual look, never ground truth for code.

## Stack

- Backend `backend/`: Python 3.12+, FastAPI, SQLite (SQLAlchemy + aiosqlite,
  alembic), pytest
- Frontend `frontend/`: React + TypeScript + Vite, TanStack Query, vitest
- User docs `docs/user/`: Markdown built with zensical
- Windows exe `installer/`: PyInstaller
- Master plan: `plan.md` · phases & status:
  [docs/dev/implementation-plan.md](docs/dev/implementation-plan.md)

## Hard rules

- **Never sign commits as Claude.** No `Co-Authored-By: Claude` trailer, no
  "Generated with Claude Code" line. This overrides any default behavior.
- Conventional commits (`feat:`, `fix:`, `docs:`, …), one logical change per
  commit. See [git workflow](docs/dev/git-workflow.md).
- Feature work happens on `feat/<name>` branches, merged into `main`.
- Plan a feature and discuss it with the user **before** implementing it.
  Discuss improvement ideas with the user too.
- Everything swappable stays behind an interface: song sources, the USDX
  launcher, player selectors, auth providers. See
  [architecture](docs/dev/architecture.md).
- **Python only through the repo venv, by absolute path:**
  `D:\git\Ultrastar-Wingman-new\venv\Scripts\python.exe`. Never system
  python, never activation scripts.
- Write files with the Write/Edit tools, not PowerShell `Set-Content` (it
  mangles UTF-8).
- No new dependency without a reason a few lines of code can't cover.
- The user's live data (`WINGMAN_DATA_DIR`, ports 8080/5173) is read-only for
  verification runs — see [verifying](docs/dev/verifying.md).

## Codebase map

### Backend — `backend/src/ultrastar_wingman/`

One package per domain. Each has the same four files: `api.py` (thin FastAPI
handlers: parse, authorize via `Depends(require("<capability>"))`, call the
service, return), `service.py` (business logic, never imports FastAPI),
`model.py` (SQLAlchemy tables), `schema.py` (Pydantic read models, FastAPI-free
so services and the event bus can use them).

| Module | Owns |
|---|---|
| `app.py`, `api.py`, `__main__.py` | app factory + lifespan (migrations, startup scan, download worker), router aggregation under `/api/v1`, the WebSocket endpoint, the entry point |
| `config.py` | bootstrap settings from env `WINGMAN_*` (paths, bind address, open-browser) — everything else is a runtime setting |
| `settings.py` | DB-backed settings registry: `register(SettingDefinition(...))` at import time, `SettingsService` reads/writes, emits `setting.changed` |
| `db.py` | declarative base, migration runner, `SessionDep` |
| `events.py` | typed WebSocket event bus, server → client only: `class Foo(Event)` with a `Literal` name, `await event_bus.broadcast(Foo(...))` |
| `auth/` | accounts, sessions, host token, OIDC. `deps.py` is the **only** place permissions are checked; `permissions.py` lists capabilities (`songs.view`, `karaoke.sing`, `settings.manage`, …) and role defaults; `providers.py` is the auth-provider seam |
| `songs/` | the library: `.txt` parsing (`txt.py`, `is_duet` included — singer-switch body lines or both duet-singer headers), content fingerprint, directory scanner (every scan re-parses every txt, so a column added to the parser fills itself on the next start), `songs` table. `SongRead` carries what the built-in facets filter on — `is_duet`, `has_video`, `genre`, `language`, `edition`, `year` — on every row of every listing. `txt.py` also writes: `load_song_txt` proves the file's bytes round-trip before anything may touch it, `rewrite_headers` sets or removes named headers and leaves every other byte (BOM, line endings, unknown headers, body) alone. `service.py` is the two library changes that are not a scan — deleting a song (`songs.delete`): the folder off the disk under the scanner's lock, then the row, then the wishes — every other referencing row survives as an orphan its listing already skips, so a re-download under the same id finds its history again — and editing its metadata (`songs.edit`, `PATCH /songs/{id}`): the six `SongMetadata` headers into the txt, then the row (and its `fingerprint`) from the file as written, so the next scan is a no-op; the request carries the `expected` values the editor was opened on and a file that has moved on since is a 409 |
| `sources/` | song-source seam (`base.py`) + registry; `progress.py` maps a source's steps onto one 0–100 bar; `usdb.py` is the USDB implementation |
| `downloads/` | persistent download queue + worker; `media.py` manages yt-dlp/ffmpeg |
| `karaoke/` | launcher seam (`launcher.py`) + USDX implementation (`usdx.py` process, `usdx_config.py` config.ini rewrite, `usdx_paths.py`, `usdx_scores.py` import from `Ultrastar.db`), the sing flow, sessions/sings/scores tables, slots & colors. A score also carries where it came in — `placement` (1 is the best, ties share it: `model.placements` is standard competition ranking, so 1, 1, 3) and `field_size` (how many scores that sing had, the empty-slot placeholder excluded, walk-ins included) — written once by `service._finish` when the sing's scores are imported and never recomputed, which is what lets a win outlive the losing score being deleted or reassigned; migration 0026 backfilled the history under the same rule |
| `players/` | players (guest + registered), avatars, and `hidden` — the flag `PATCH /players/{id}` (`players.manage`) sets to take somebody out of the singer picker and out of nothing else; `auth.service.start_session` clears it for the player of whoever logs in |
| `library/` | wishlist, favorites, playlists |
| `tags/` | global song tags: the `tags` / `tag_permissions` / `song_tags` tables, per-tag `view` / `view_songs` / `assign` (`service.allowed`), and `hidden_song_ids` — the songs a caller may not see, applied through `auth.deps.HiddenSongsDep` and `songs.api.song_or_404`. `builtin.py` is the eight built-ins as one table (`BUILT_INS`) — the marks `favorites` / `sung` (`color` + `show_in_list`), the boolean facets `duet` / `video` (those two + `show_in_filter`) and the valued facets `genre` / `language` / `edition` / `decade` (`show_in_filter`): `KIND_OPTIONS` says which options a kind has, and drives both the settings keys and the 422 on an option a kind lacks. Stored as settings under a private definitions dict (so the settings API never sees them), read by everybody on `GET /tags`, written on `PATCH /tags/built-in/{id}` (`tags.manage`). No SQL and no values endpoint behind a facet — the filtering and the value lists are the client's, over `SongRead` |
| `comments/` | what people say about a song: the `song_comments` table, `comments.write` to add one and `comments.moderate` to delete somebody else's (your own is always yours) |
| `stats/` | statistics over what `karaoke` recorded. Which parties a caller may open is `visible_session_ids` in `api.py`: the one still going (`stats.view`), the ones a signed-in account sang at (a `scores.player_id` of their player — identity, not a capability), and every one of them with `stats.history`; `GET /stats/scores` is those same parties added up ("All parties" / "All my scores"), its own route rather than a reserved session id. Read-only apart from naming a session (`stats.manage`, which broadcasts `sessions.changed` so the picker in the room reads the new name), keeping one out of that picker (`stats.hide`) and the two corrections `stats.moderate` may make to a recorded score — `PATCH /stats/scores/{id}` puts it on another player (the number, the song, the sing and the party stay), `DELETE` takes the score alone off the record and leaves the sing standing. Neither touches the `placement` or `field_size` of any score of that sing, by design: they are the field the song was sung against, and the deleted row is exactly what would be needed to work them out again. Both broadcast `scores.changed`. `PUT /stats/sessions/{id}/hidden` (`stats.hide`, its own route so `stats.manage` can never reach it) is the party picker's tidy-up and reaches **that one listing** — `GET /stats/sessions` drops a hidden party unless `?include_hidden=true` *and* the caller holds `stats.hide`, while `SessionList`'s `session_count` / `score_count` (the head row's line) and everything else — `/stats/scores`, `visible_session_ids`, a player's own scores, a song's best scores, the achievements pass — count it as before; the flag is dormant on the party being sung, which is therefore never dropped from the listing and whose hiding is a 409; broadcasts `sessions.changed` |
| `achievements/` | what a player earns by singing ([the design](docs/dev/achievements.md)). `model.py` is the two tables — the catalogue, and one `player_achievements` row per (enabled achievement, player who has a score), `earned_at` NULL while it carries progress only. `schema.py` is the condition language (`Condition`: scope, metric, comparator, value, the score/song filters — a song clause's `regex` operator among them, whose cost is counted over `re`'s own parse tree and refused at the door, a running match being uninterruptible) and is the only way a stored `definition` is read — an unreadable one is "never satisfied", never an exception; `read_achievement` is also where the `hidden` masking is applied. `evaluate.py` is the pure engine over one player's `ScoreRow`s: all conditions hold, the session-scoped ones inside one and the same party, progress is the least complete condition. `service.py` is the one query that feeds it, the pass that writes the rows (recomputation, so revoking works; a module lock serialises passes and the global toggle is checked inside them) and the catalogue's own writes. `builtin.py` is the seventeen Wingman ships, as data — migration 0023 seeds them as ordinary rows with slug ids and `built_in = True`, which buys three things: `DELETE` on one is a 409, its **conditions** are that file's (a `definition` sent to one is a 409 from `PATCH`, and `import_archive` writes every other field of a built-in but leaves its stored conditions alone — creating one under a shipped id included), and `POST /achievements/{id}/reset` puts name, description, icon, colour, `hidden` and the definition back out of `builtin.py` and drops an uploaded picture, leaving `enabled` and `sort_order` alone — the order of the catalogue is the host's (see below), not the achievement's. Reset is therefore also the only way an improved shipped definition reaches a database the seed already ran on. `settings.py` is the three private settings (`enabled`, the two host-screen second counts), the `tags/builtin.py` pattern. `api.py` is the catalogue, its icons (uploaded through the shared `images.py`), `POST /achievements/{id}/reset`, `PUT /achievements/order` — the arranging write over `sort_order` (the only other one is an import, which takes the places its archive carries; a create lands at the end and `POST`/`PATCH` carry no such field), the whole catalogue as one permutation (422 `order_mismatch` for anything else), answering the managing listing and starting no pass, because where a badge sits in the list says nothing about who earned it — `PATCH /achievements/settings` and `GET /players/{id}/achievements`; reading takes no capability, writing takes `achievements.manage` — and so does `GET /achievements?manage=true`, the one unmasked answer there is: holding the capability unmasks nothing, because the administrator and the host screen read this same catalogue on the user page and on the TV, so a `hidden` achievement is blank for them too until their own player earns it (a player's record is masked over its *subject* for every reader alike, definition included). Two events: `achievements.earned` (per sing, from `karaoke.service._finish`) and `achievements.changed` — no payload, the `tags.changed` precedent, from every write that changes what `GET /achievements` answers (create, edit, reset, reorder, delete, both icon routes, the settings PATCH), because the masking is per caller. Re-evaluated from four places: `_finish`, the two `stats.moderate` corrections, and every catalogue write — that last one as a tracked background pass. `images/` is the shipped artwork — one full-size PNG per built-in, named by its id, and `images/small/` the same at 256 px, made by [the artwork guide](docs/dev/achievement-artwork.md) — and `pictures.py` is what reads it: a built-in is drawn with its shipped picture unless the host uploaded one (`picture_of`, behind `has_image` / `image_shipped` / `icon_version` and `GET /achievements/{id}/icon?size=small|full`), so reset and removing an upload go *back* to it, export carries uploads only, and the installer spec lists the directory in `datas` |
| `images.py` | the rules every uploaded picture follows — the content-type allowlist the bytes have to agree with, the byte cap, the pixel cap read out of the file's own header, and storing one file per subject. Used by the player avatars and the achievement icons; no image library, header parsing only |
| `frontend.py`, `join_url.py` | serving `frontend/dist`; the address the host screen advertises |
| `migrations/versions/` | alembic, `NNNN_<what>.py` |

Tests: `backend/tests/test_<module>*.py`. `conftest.py` gives `client` (admin),
`anonymous_client`, `session`, `broadcast_events`; captured external samples
live in `tests/fixtures/`.
