# Ultrastar Wingman

Companion app for Ultrastar Deluxe (USDX): song downloads, player management,
statistics, and a web UI for controlling karaoke sessions. Ground-up rewrite of
`D:\git\ultrastar-wingman` — the old project is inspiration for behaviour and
for the visual look, never ground truth for code.

## Stack

- Backend `backend/`: Python 3.12+, FastAPI, SQLite (SQLAlchemy + aiosqlite,
  alembic), pytest
- Frontend `frontend/`: React + TypeScript + Vite, TanStack Query, vitest
- User docs `docs/user/`: Markdown built with zensical
- Windows exe + installer `installer/`: PyInstaller, Inno Setup 6
- Phases & status: [docs/dev/implementation-plan.md](docs/dev/implementation-plan.md)

## Hard rules

- **Never sign commits as Claude.** No `Co-Authored-By: Claude` trailer, no
  "Generated with Claude Code" line. This overrides any default behavior.
- Conventional commits (`feat:`, `fix:`, `docs:`, …), one logical change per
  commit. See [git workflow](docs/dev/git-workflow.md).
- Feature work happens on `feat/<name>` branches, merged into `main`.
- Plan a feature and discuss it with the user **before** implementing it.
  Discuss improvement ideas with the user too.
- Everything swappable stays behind an interface: song sources, the USDX
  launcher, player selectors, auth providers. See
  [architecture](docs/dev/architecture.md).
- **Python only through the repo venv, by absolute path:**
  `D:\git\Ultrastar-Wingman-new\venv\Scripts\python.exe`. Never system
  python, never activation scripts.
- Write files with the Write/Edit tools, not PowerShell `Set-Content` (it
  mangles UTF-8).
- No new dependency without a reason a few lines of code can't cover.
- The user's live data (`WINGMAN_DATA_DIR`, ports 8080/5173) is read-only for
  verification runs — see [verifying](docs/dev/verifying.md).

## Codebase map

### Backend — `backend/src/ultrastar_wingman/`

One package per domain. Each has the same four files: `api.py` (thin FastAPI
handlers: parse, authorize via `Depends(require("<capability>"))`, call the
service, return), `service.py` (business logic, never imports FastAPI),
`model.py` (SQLAlchemy tables), `schema.py` (Pydantic read models, FastAPI-free
so services and the event bus can use them).

| Module | Owns |
|---|---|
| `app.py`, `api.py`, `__main__.py` | app factory + lifespan (migrations, startup scan, download worker), router aggregation under `/api/v1`, the WebSocket endpoint, the entry point — whose one argument, `--usdx-dir`, it writes into `WINGMAN_USDX_DIR` before the settings are first read, because uvicorn calls the factory with nothing |
| `console.py` | the console window's one line format, for Wingman's loggers and uvicorn's alike (`__main__` calls `configure` and hands uvicorn `log_config=None`): `HH:MM:SS  message`, the level only when it is not INFO, the logger only at `WINGMAN_LOG_LEVEL=debug`; every other library at WARNING; `UvicornFilter` turns uvicorn's "running on" line into `Wingman is running at http://localhost:<port>` and leaves its process chatter, WebSocket handshakes (their query stripped there too) and the `websockets` library's "connection open" (logged through `uvicorn.error`) to the debug view; uvicorn's access log is off unless debug, and `AccessFilter` strips the query string there. A host follows the evening through the services' own INFO lines (a sing with its singers, its scores, its badges; a download queued / done / failed; a login, a logout, the host link; a setting's name, a volume's at DEBUG because the player's slider writes one per pause in a drag; a player selector online / offline, or online in another protocol — a WARNING, said again whenever the protocol changes; a card), so a new lifecycle line names things (`songs.schema.song_label`, a player's name) and never an id or a secret; per-request and per-heartbeat lines are DEBUG |

| `songs/` | the library: `.txt` parsing (`txt.py`, `is_duet` included — singer-switch body lines or both duet-singer headers), content fingerprint, directory scanner (every scan re-parses every txt, so a column added to the parser fills itself on the next start), `songs` table. `SongRead` carries what the built-in facets filter on — `is_duet`, `has_video`, `genre`, `language`, `edition`, `year` — on every row of every listing. `no_value` is what reads the literal `None` USDB writes into `#GENRE` / `#LANGUAGE` / `#EDITION` as no value at all — no migration, every scan re-parses — and `songs.schema.SongMetadata` applies the same rule so the editor cannot write it back. `SongTxt.preview_start` is where a preview of the song starts — `#PREVIEWSTART` as-is, else the first note placed from `#GAP`, `#BPM` and its beat less `LYRICS_LEAD_IN_SECONDS` (2, the user's choice), else `None` for the beginning — written to `songs.preview_start_seconds` by every scan (migration 0035, no backfill) and read by `karaoke.selection` for the reel's song. `txt.py` also writes: `load_song_txt` proves the file's bytes round-trip before anything may touch it, `rewrite_headers` sets or removes named headers and leaves every other byte (BOM, line endings, unknown headers, body) alone. `service.py` is the two library changes that are not a scan — deleting a song (`songs.delete`): the folder off the disk under the scanner's lock, then the row, then the wishes — every other referencing row survives as an orphan its listing already skips, so a re-download under the same id finds its history again — and editing its metadata (`songs.edit`, `PATCH /songs/{id}`): the six `SongMetadata` headers into the txt, then the row (and its `fingerprint`) from the file as written, so the next scan is a no-op; the request carries the `expected` values the editor was opened on and a file that has moved on since is a 409 |

lies), the auto-start task a roomful of known players schedules — on a report that fills the room, and on an `open_selection` the *cards* filled (a room the phone remembered from last time starts `selection.changed` carries the whole selection and never the token. A successful **forced** `POST /karaoke/sing` closes whatever was open, because `force` means "take the machine", and `start_selection` gives the lock up across `service.start_sing` (which on a forced start spans a USDX exit and a score import) and drops the selection afterwards only if it is still the same one, so a device report is never queued behind somebody's Play. `reel.py` is the one place Wingman picks a song for somebody — `pick_song(session, scope, viewer, playlist_id=)` over `schema.Scope` (`all` / `favorites` / `wishlist` / `weighted` / `playlist`) and `top_wish`: every scope drops `tags.hidden_song_ids`, `all` also drops `tags.folded_song_ids` (the reel is the song list in another shape), the others are what people picked by hand and keep a folded-away song; candidates sorted before `random.choice`, so a seeded generator reproduces a pick. A selection may be **spun**: `POST /karaoke/selection` takes `spin {scope, playlist_id}` instead of `song_id` (exactly one, else 422; `playlist_id` with the `playlist` scope and only there, else 422;
