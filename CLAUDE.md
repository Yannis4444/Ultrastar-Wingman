# Ultrastar Wingman

Companion app for Ultrastar Deluxe (USDX): song downloads, player management,
statistics, and a web UI for controlling karaoke sessions. Ground-up rewrite of
`D:\git\ultrastar-wingman` — the old project is inspiration for behaviour and
for the visual look, never ground truth for code.

## Stack

- Backend `backend/`: Python 3.12+, FastAPI, SQLite (SQLAlchemy + aiosqlite,
  alembic), pytest
- Frontend `frontend/`: React + TypeScript + Vite, TanStack Query, vitest
- User docs `docs/user/`: Markdown built with zensical
- Windows exe + installer `installer/`: PyInstaller, Inno Setup 6
- Phases & status: [docs/dev/implementation-plan.md](docs/dev/implementation-plan.md)

## Hard rules

- **Never sign commits as Claude.** No `Co-Authored-By: Claude` trailer, no
  "Generated with Claude Code" line. This overrides any default behavior.
- Conventional commits (`feat:`, `fix:`, `docs:`, …), one logical change per
  commit. See [git workflow](docs/dev/git-workflow.md).
- Feature work happens on `feat/<name>` branches, merged into `main`.
- Plan a feature and discuss it with the user **before** implementing it.
  Discuss improvement ideas with the user too.
- Everything swappable stays behind an interface: song sources, the USDX
  launcher, player selectors, auth providers. See
  [architecture](docs/dev/architecture.md).
- **Python only through the repo venv, by absolute path:**
  `D:\git\Ultrastar-Wingman-new\venv\Scripts\python.exe`. Never system
  python, never activation scripts.
- Write files with the Write/Edit tools, not PowerShell `Set-Content` (it
  mangles UTF-8).
- No new dependency without a reason a few lines of code can't cover.
- The user's live data (`WINGMAN_DATA_DIR`, ports 8080/5173) is read-only for
  verification runs — see [verifying](docs/dev/verifying.md).

## Codebase map

### Backend — `backend/src/ultrastar_wingman/`

One package per domain. Each has the same four files: `api.py` (thin FastAPI
handlers: parse, authorize via `Depends(require("<capability>"))`, call the
service, return), `service.py` (business logic, never imports FastAPI),
`model.py` (SQLAlchemy tables), `schema.py` (Pydantic read models, FastAPI-free
so services and the event bus can use them).

| Module | Owns |
|---|---|
| `app.py`, `api.py`, `__main__.py` | app factory + lifespan (migrations, startup scan, download worker), router aggregation under `/api/v1`, the WebSocket endpoint, the entry point — whose one argument, `--usdx-dir`, it writes into `WINGMAN_USDX_DIR` before the settings are first read, because uvicorn calls the factory with nothing — and which does what `uvicorn.run` did around the server (the same `Config` — but `forwarded_allow_ips` `*` unless uvicorn's own `FORWARDED_ALLOW_IPS` says otherwise, so a reverse proxy on another machine makes the OIDC redirect_uri `https`; nothing is granted by address —, a Ctrl+C after the start a clean exit, exit 3 for a server that never started) but runs `startup.WingmanServer` on the sockets `startup.listen` took, closing them afterwards whatever happened |
| `console.py` | the console window's one line format, for Wingman's loggers and uvicorn's alike (`__main__` calls `configure` and hands uvicorn `log_config=None`): `HH:MM:SS  message`, the level only when it is not INFO, the logger only at `WINGMAN_LOG_LEVEL=debug`; every other library at WARNING; `UvicornFilter` says uvicorn's "Shutting down" as *Wingman is stopping* and leaves its process chatter, WebSocket handshakes (their query stripped there too) and the `websockets` library's "connection open" (logged through `uvicorn.error`) to the debug view; uvicorn's access log is off unless debug, and `AccessFilter` strips the query string there. ### Firmware — `firmware/`

The player selector device: a PlatformIO project, Arduino core 3.x on the
pioarduino platform, built by `build.py` into the backend package and never
committed. The rules are [firmware.md](docs/dev/firmware.md), the design
[player-selector.md](docs/dev/player-selector.md).

| Path | Owns |
|---|---|
| `src/` | `pins.h` (the fixed pin map and `PROTOCOL_VERSION`), the pure modules the host tests cover — `CardTracker` (per-reader state machine), `Buttons` (debounce), `Report` (the report JSON and when one is due), `Response` (the answer's `interval_s`, `leds` and `update` read out of the JSON) — and the glue: `ReaderBus` (MFRC522v2 probe and poll), `Config` (NVS), `Net` (Wi-Fi, the POST, backoff), `SerialConsole` (the JSON-lines protocol over USB), `Leds` (the optional NeoPixel strip on GPIO 13, one light per reader), `Updater` (HTTPUpdate over Wi-Fi with the device's bearer token), `main.cpp` |
| `test/test_native/` | Unity tests of the three pure modules, run on the host by `pio test -e native` |
| `scripts/`, `build.py` | the PlatformIO pre/post scripts (version, merged image) and the bundler that writes `wingman-esp32.bin` and `manifest.json` into `backend/src/ultrastar_wingman/devices/firmware/` |

Keep this map at module granularity and update it in the same commit when a
module, page or route is added, renamed or removed.
